## 1. نظرة عامة على البنية المعمارية (System Architecture)

تعتمد **منصة UST للمحاضرات** على بنية متكاملة تفصل بوضوح بين طبقة العرض (Frontend)، وطبقة التحقق والملفات والنسخ الاحتياطي (Express Server)، وطبقة المصادقة وقواعد البيانات السحابية (Firebase Auth + Firestore):

1. **الواجهة الأمامية (React 19 + Vite + TypeScript + Tailwind CSS)**:
   - واجهة طلاب عربية متكاملة تدعم القراءة من اليمين إلى اليسار (`RTL`) والتسلسل الأكاديمي الخماسي (`التخصص ← السنة ← الفصل ← المادة ← الملفات`).
   - نافذة تسجيل دخول رسمية عبر Google (`LoginModal.tsx`) تعرض شعار المنصة ورابطي **شروط الاستخدام** و**سياسة الخصوصية** داخل النافذة.
   - لوحة تحكم هرمية متعددة المستويات (`AdminDashboard.tsx` & `ModeratorDashboard.tsx`) تتكيّف تلقائياً مع دور المستخدم وصلاحياته الفعلية.

2. **الخادم الوسيط الآمن (Express + `server.ts` + `server/firebaseAdmin.ts` + `server/storageManager.ts`)**:
   - التحقق من رموز Firebase ID Tokens الموثقة من Google على الخادم (`adminAuth.verifyIdToken`).
   - فرض الحماية ضد تجاوز المعدل (`Sliding-Window Rate Limiting`) على مسارات المصادقة، وإدارة المسؤولين، والرفع، والنسخ الاحتياطي.
   - إدارة التخزين المنظم هرمياً للمحاضرات، وفحص السعة المتاحة لحظياً على القرص قبل القبول الفعلي لأي ملف، وحساب بصمات `SHA-256` لمنع التكرار.
   - إنشاء وإدارة النسخ الاحتياطية المنفصلة (قاعدة البيانات JSON + حزم ملفات المحاضرات مع ملف `manifest.json`)، وسجلات التدقيق الإداري غير القابلة للتعديل.

3. **قاعدة البيانات السحابية وقواعد الأمان (`Firebase Firestore` + `firestore.rules`)**:
   - قواعد أمان صارمة تحمي وثائق الأدوار والصلاحيات والإعدادات والسجلات، وتمنع أي ترقية ذاتية (`Self-Promotion`) عند التسجيل أو تعديل الملف الشخصي.
   - *(ملاحظة بيئة التشغيل: تم اعتماد Firebase Firestore كقاعدة بيانات الإنتاج المباشرة بدلاً من Cloud SQL PostgreSQL لتجاوز قيود الحصة السحابية في المشروع، مع إرفاق مخطط PostgreSQL + RLS مرجعي كامل في `docs/reference_postgresql_rls_schema.sql` في حال الترحيل مستقبلاً).*

## 2. المصادقة عبر Google ونظام المالك الرئيسي (`Super Admin`)

### تدفق المصادقة الآمن (Authentication Flow)
1. يضغط المستخدم على زر **"المتابعة باستخدام Google"**.
2. تتم المصادقة عبر نافذة Google OAuth الموثقة من Firebase Auth (`signInWithPopup` + `GoogleAuthProvider`).
3. يستدعي العميل نقطة النهاية المحمية `POST /api/auth/sync` ممرراً رمز الهوية الموقّع (`Authorization: Bearer <idToken>`).
4. على الخادم:
   - يتم التحقق من صحة التوقيع ومن حالة `email_verified === true`.
   - يُمنح كل مستخدم جديد دور **`student` (طالب)** افتراضياً وبشكل إجباري.
   - إذا كان البريد الإلكتروني مطابقاً للمتغير البيئي `SUPER_ADMIN_EMAIL` (الافتراضي: `mohammednourr56000@gmail.com`)، يُفعّل تلقائياً كـ **`super_admin` — المدير الرئيسي / مالك المنصة** مع كامل الصلاحيات الـ 20.
   - إذا وُجدت دعوة بريدية معلّقة صالحة في مجموعة `adminInvitations` لهذا البريد الموثّق، يتم تفعيل الصلاحيات المحددة في الدعوة تلقائياً بعد إتمام تسجيل الدخول بنجاح.
   - يُمنع منعاً باتاً إسناد أو تعديل دور `super_admin` من أي واجهة مستخدم عامة أو من شاشة إدارة المسؤولين.

### إعداد متغيرات البيئة (`.env`)
انظر `.env.example`:
- `SUPER_ADMIN_EMAIL`: البريد الإلكتروني المعتمد لحساب Google المالك للمنصة.
- `GEMINI_API_KEY`: مفتاح Gemini AI للتحليل الأكاديمي وتلخيص ملفات المحاضرات على الخادم.
- `APP_URL`: الرابط المعتمد للتطبيق.

## 3. النظام الهرمي للأدوار والصلاحيات (3-Tier RBAC)

| المستوى | الدور (`UserRole`) | الوصف والصلاحيات الافتراضية |
| :--- | :--- | :--- |
| **المستوى 1** | `super_admin` (المدير الرئيسي / مالك المنصة) | تحكم مطلق لا يمكن تقييده أو حذفه أو إيقافه. يمتلك جميع الصلاحيات الـ 20 ويدير المسؤولين والإعدادات والسجلات والنسخ الاحتياطي. |
| **المستوى 2** | `admin` (مسؤول إداري) | لوحة إدارة كاملة مفلترة حسب الصلاحيات الـ 20 الممنوحة له، يمكن تعيينه عبر اختيار مستخدم حالي أو إرسال دعوة بريدية لحساب Google جديد مع اختيار قالب صلاحيات جاهز أو مخصص. |
| **المستوى 3** | `moderator` (مشرف رفع محتوى) | واجهة إشراف مخصصة ومركّزة (`ModeratorDashboard.tsx`) لرفع وتنظيم ملفات المحاضرات ومتابعة ملفاته وسجل رفعه وسعة التخزين دون وصول لإدارة المسؤولين أو النظام الحساس. |
| **الافتراضي** | `student` (طالب) | تصفح المحاضرات المنشورة، معاينتها، تحميل الملفات المسموح بتحميلها، الإشارات المرجعية، والملف الشخصي فقط. |

### مصفوفة الصلاحيات الـ 20 الدقيقة (`ALL_PERMISSIONS`)
1. **إدارة المستخدمين والأدوار**: `users.view`, `users.manage`, `roles.assign`
2. **إدارة الهيكل الأكاديمي**: `specializations.create`, `specializations.edit`, `specializations.delete`, `academic_years.manage`, `semesters.manage`, `subjects.create`, `subjects.edit`, `subjects.delete`
3. **إدارة المحاضرات والتخزين**: `lectures.upload`, `lectures.edit`, `lectures.publish`, `lectures.delete`, `storage.view`, `storage.manage`
4. **إدارة النظام والمراقبة**: `announcements.manage`, `settings.manage`, `audit_logs.view`

## 4. بنية التخزين المنظمة وحماية السعة (Structured Storage & Quotas)

تُخزّن ملفات المحاضرات والنسخ الاحتياطية وفق مسارات هرمية منظمة ومعزولة داخل الجذر:
```text
uploads/
└── ust-storage/
    ├── specializations/
    │   └── {specializationId}/
    │       └── {academicYearId}/
    │           └── {semesterId}/
    │               └── {subjectId}/
    │                   └── ust_{timestamp}_{uuid}.{ext}
    ├── tmp/                     (منطقة فحص مؤقتة قبل النقل النهائي)
    ├── index/                   (فهارس الخادم السريعة للسجلات والدليل والنسخ)
    └── backups/
        ├── db/                  (نسخ قواعد البيانات JSON)
        └── files/               (لقطات ملفات المحاضرات + manifest.json)
```

### سياسة السعة والتنبيهات
- يحسب الخادم المساحة المستخدمة فعلياً على القرص لملفات المحاضرات (مستثنياً مجلد النسخ الاحتياطية).
- **عتبات التنبيه**: `70%` (تنبيه استهلاك)، `85%` (تحذير مرتفع)، `95%` (حرج)، و**`100%` (إيقاف تلقائي للرفع)** مع إرجاع رسالة رفض عربية دقيقة برمز HTTP `403`:
  > *"عذراً، مساحة التخزين المتاحة غير كافية. يرجى مراجعة مسؤول المنصة."*
- **منع التكرار**: يُحسب هاش `SHA-256` لكل ملف عند الرفع، وتعرض لوحة التخزين قائمة الملفات المتطابقة لإتاحة المراجعة والتنظيف.

## 5. النسخ الاحتياطي والاسترجاع (Backup & Recovery)

توفر لوحة الإدارة ثلاثة أنواع مستقلة من النسخ الاحتياطية:
1. **نسخة قاعدة البيانات (`db`)**: تُصدّر جميع المجموعات الأساسية (التخصصات، السنوات، الفصول، المواد، بيانات الملفات، المستخدمين، المسؤولين، الدعوات، الإعدادات، الإعلانات) في ملف JSON مؤرخ وقابل للتحميل المباشر.
2. **نسخة ملفات المحاضرات (`files`)**: تنسخ جميع الملفات الفيزيائية الحالية في لقطة مؤرخة تحت `uploads/ust-storage/backups/files/{backupId}/` وتنشئ ملف `manifest.json` يضم اسم كل ملف ومساره النسبي وحجمه وبصمة `SHA-256`.
3. **نسخة كاملة (`full`)**: تجمع اللقطتين معاً لضمان استعادة متزامنة ومتطابقة للمعلومات والملفات.

## 6. التحقق قبل التشغيل والنشر (Verification & Deployment)

1. تشغيل اختبارات المنطق والخادم:
   ```bash
   npx --yes tsx --test src/utils/academicLogic.test.ts server/storageManager.test.ts
   ```
2. تدقيق قواعد أمان Firestore ونشرها:
   ```bash
   npx eslint firestore.rules
   ```
3. البناء الإنتاجي:
   ```bash
   npm run build
   ```
4. التشغيل الإنتاجي للخادم (متضمن الواجهة المبنية):
   ```bash
   npm start
   ```
